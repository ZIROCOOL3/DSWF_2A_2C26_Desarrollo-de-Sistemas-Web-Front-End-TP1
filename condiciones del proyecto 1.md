# Trabajo Práctico Grupal 1

Proyecto web en equipo · HTML, CSS y JavaScript

Construyan un sitio web grupal con una portada, perfiles individuales, navegación interna y una bitácora que permita reconocer cómo trabajaron.

**Estado:** consigna disponible **Fechas:** se comunicarán por Moodle **Entrega:** un único enlace al repositorio grupal

01

## Leé antes de empezar {#consigna}

**Este es el primer trabajo práctico grupal.** Organicen el proceso antes de crear archivos: el repositorio, los commits, la bitácora y la documentación deben hacer visible el trabajo compartido.

### Qué tienen que hacer, paso a paso

1.  **Lean toda la consigna** y acuerden roles, tiempos y una forma de comunicación antes de iniciar el proyecto.
2.  **Creen un repositorio público e independiente** para este TP1. Cada integrante debe participar y tener su perfil de GitHub enlazado en el README.
3.  **Organicen los archivos:** `index.html` y las páginas individuales en la raíz; CSS y JavaScript en carpetas separadas; imágenes en `img`.
4.  **Construyan la portada:** debe presentar el nombre, el propósito del equipo y un listado completo de integrantes con enlaces a sus perfiles.
5.  **Desarrollen una tarjeta individual por integrante** con foto o avatar, nombre, ciudad, edad, cuatro habilidades, tres películas favoritas y tres discos favoritos.
6.  **Incluyan botones de navegación** en todas las secciones. Nadie debe depender del botón Atrás del navegador para recorrer el sitio.
7.  **Incorporen JavaScript:** al menos una interacción dinámica en la portada y una en cada perfil. Todas deben explicarse en el README.
8.  **Diseñen para distintos tamaños de pantalla** y revisen los breakpoints de 400 px, 900 px y 1200 px.
9.  **Registren el proceso** en una sección Bitácora accesible desde el menú principal.
10. **Publiquen con Vercel** y documenten su URL en el README. Para entregar, carguen solamente el enlace del repositorio grupal en la planilla única.

## Requisitos del proyecto {#requisitos}

La consigna evalúa una base técnica clara, navegación comprensible, una presentación uniforme del equipo y un proceso que pueda revisarse desde el repositorio.

PORTADA

### Inicio y navegación

- `index.html` en la raíz, con nombre y breve propósito del equipo.
- Listado de todas las personas integrantes con enlaces funcionales a sus páginas.
- Botones internos y menú que permitan ir y volver sin depender del navegador.

PERFILES

### Tarjeta de cada integrante

- Foto, avatar o mascota; nombre, ciudad y edad.
- Al menos cuatro habilidades, tres películas y tres discos favoritos.
- Una función dinámica propia y una presentación clara, consistente y legible.

DISEÑO

### CSS y diseño adaptable

- CSS propio, organizado y aplicado correctamente en todas las páginas.
- Google Fonts, colores, márgenes y tamaños con una decisión visual consistente.
- Breakpoints obligatorios en 400 px, 900 px y 1200 px, sin desbordes.

BITÁCORA

### Proceso y publicación

- Bitácora en un HTML propio, enlazado desde el menú, con decisiones, dificultades y cambios.
- Repositorio GitHub independiente y publicación en Vercel.
- Avatares, ilustraciones o mascotas son válidos y recomendables si prefieren no usar fotos personales.

## Cómo se evalúa {#rubrica}

La rúbrica contempla el funcionamiento del sitio, su presentación, la documentación y la evidencia de colaboración dentro del repositorio.

Gestión de repositorio y publicación+

1.  No cumple: no hay un enlace al repositorio, no carga o el repositorio no es independiente.
2.  Cumple: el repositorio existe, pero está desorganizado o faltan commits del equipo.
3.  Propone: repositorio independiente, publicado en Vercel y correctamente documentado en el README.
4.  Supera: historial de commits impecable, ordenado y con participación activa de todo el equipo.

Estructura de navegación y enlaces+

1.  No cumple: no hay botones de navegación o hay que usar obligatoriamente el botón Atrás.
2.  Cumple: faltan botones en algunas secciones o hay enlaces rotos.
3.  Propone: navegación fluida con botones internos en todas las secciones.
4.  Supera: menú muy intuitivo, con una experiencia de uso especialmente cómoda.

Portada principal y listado+

1.  No cumple: no está el index.html en la raíz o no presenta al equipo.
2.  Cumple: está la portada, pero faltan integrantes o los enlaces a sus páginas no funcionan.
3.  Propone: incluye nombre del equipo, propósito y listado con todos los enlaces correctos.
4.  Supera: diseño de portada excelente, creativo y con una identidad visual de grupo marcada.

Tarjeta de presentación individual+

1.  No cumple: faltan las páginas de integrantes o están vacías.
2.  Cumple: falta información obligatoria, como edad, ubicación, habilidades o intereses mínimos.
3.  Propone: cada integrante tiene foto o avatar, nombre, edad, ubicación, habilidades, películas y discos.
4.  Supera: maquetación prolija, uniforme y visualmente atractiva en todos los perfiles.

Diseño adaptativo y breakpoints+

1.  No cumple: no es responsive o se rompe por completo en celulares.
2.  Cumple: intenta adaptarse, pero tiene desbordes o textos superpuestos en algún breakpoint.
3.  Propone: el sitio se adapta correctamente a 400 px, 900 px y 1200 px sin errores.
4.  Supera: adaptabilidad fluida e impecable, optimizada para distintos dispositivos.

Estética, estilos CSS y tipografía+

1.  No cumple: usa estilos por defecto del navegador o fuentes genéricas.
2.  Cumple: el diseño es descuidado o el CSS está desordenado y sin estructura clara.
3.  Propone: colores armónicos, uso correcto de Google Fonts y CSS prolijo.
4.  Supera: estética profesional, gran consistencia visual y uso destacado de iconografía.

Interactividad dinámica con JavaScript+

1.  No cumple: no hay interactividad con JavaScript o los scripts dan errores en consola.
2.  Cumple: hay JavaScript sólo en la portada o sólo en los perfiles, o las funciones son muy básicas.
3.  Propone: al menos una función dinámica en la portada y una por cada perfil.
4.  Supera: lógica creativa que aporta dinamismo real a la experiencia de uso.

Sección bitácora de desarrollo+

1.  No cumple: la sección Bitácora no existe o está vacía.
2.  Cumple: es muy vaga y menciona pocos detalles del proceso o las dificultades.
3.  Propone: registra decisiones de diseño, problemas encontrados y cómo se resolvieron.
4.  Supera: relato claro, maduro y excelentemente integrado en el diseño del sitio.

Documentación obligatoria (README.md)+

1.  No cumple: no hay README o está muy incompleto. El proyecto queda desaprobado.
2.  Cumple: faltan funciones de JavaScript, capturas de pantalla o información clave.
3.  Propone: README completo con título, descripción, integrantes, tecnologías, estilos, capturas, funciones y URL de Vercel.
4.  Supera: documentación excelente, bien formateada en Markdown y útil como guía técnica.

Uso de IA y criterio de privacidad+

1.  No cumple: no se menciona la IA utilizada.
2.  Cumple: se nombran herramientas, pero no se explica cómo ayudaron en código o contenido.
3.  Propone: documenta herramientas, modelos, aportes en código y diseño, e imágenes o avatares con criterio.
4.  Supera: integración analítica y madura de IA como asistente técnico sin perder la autoría del equipo.

## Uso de IA y autoría {#ia}

REQUISITO TRANSVERSAL

### Pueden usar IA, pero tienen que explicar cómo la usaron.

- ✓En el **README.md**, nombren aplicaciones y modelos, y expliquen qué contenido, código o debugging asistieron.
- ✓Indiquen si las herramientas se usaron con plan gratuito o pago y qué experiencia previa tenía el equipo.
- ✓Si usaron avatares, logos o imágenes, describan el modelo y el criterio de los prompts.
- ✓Expliquen qué revisaron, adaptaron o cambiaron con criterio propio antes de incorporar resultados.

La IA puede ser un asistente técnico y creativo. La autoría se sostiene cuando el equipo comprende, prueba y documenta las decisiones que toma.
